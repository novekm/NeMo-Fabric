The `nvidia.fabric.claude` adapter uses the Claude Agent SDK and its bundled
Claude Code runtime. NeMo Fabric preserves Claude's native credential precedence and
forwards only supported operating-system, configuration, and authentication
variables plus values explicitly configured in `environment.env` or named by
`environment.env_names`.

The adapter package's `harness` and `full` extras pin
`claude-agent-sdk==0.2.166`. Use the same version for an environment-managed
SDK. The SDK owns and selects its compatible Claude Code runtime.

## Install the Adapter

To install the NeMo Fabric runtime, Claude adapter, and supported Claude Agent
SDK in one environment:

```bash
pip install "nemo-fabric[claude]"
```

To install the adapter and supported Claude Agent SDK without the NeMo Fabric
runtime, use the adapter package's `harness` extra:

```bash
pip install "nemo-fabric-adapters-claude[harness]"
```

The adapter package's `full` extra installs the same dependencies as `harness`;
it does not install the NeMo Fabric runtime. Both extras install the supported
`nemo-relay` CLI. Claude does not import the Relay Python API, so this adapter
does not provide a separate `relay` extra.

If the environment already manages a compatible Claude Agent SDK, install only
the adapter:

```bash
pip install nemo-fabric-adapters-claude
```

The bare adapter package does not install the NeMo Fabric runtime or SDK.

If the existing compatible Claude Agent SDK and NeMo Fabric runtime share an
environment, install the runtime and bare adapter together:

```bash
pip install nemo-fabric nemo-fabric-adapters-claude
```

For separate environments, set `ADAPTER_PYTHON` in the runtime environment to
the adapter environment's Python interpreter. Use
matching NeMo Fabric release versions for the runtime and adapter package
unless a different pairing has been explicitly validated.

## Configure the Adapter

Select the Claude harness integration in `HarnessConfig`:

```python
from nemo_fabric import HarnessConfig

harness = HarnessConfig(adapter_id="nvidia.fabric.claude")
```

Use normalized `FabricConfig` fields to configure the model, workspace, skills,
MCP servers, instructions, turn limit, tool policy, and telemetry. The
resolved Claude descriptor accepts only these Claude-specific
`harness.settings` keys:

The runtime starts even when some configured MCP servers cannot connect. After each turn, the adapter reads Claude Code's own MCP connection state (`get_mcp_status()`). Each result lists the configured servers that Claude Code could not use under `output.mcp.unavailable_servers`, with the server `name`, `transport`, and `reason` (`failed`, or `authentication_required` for a server that needs authentication). The adapter also writes a warning to standard error the first time a server is unavailable in a runtime. Error messages are not reported, because they can contain URLs, headers or other credentials. Servers that are still connecting are not reported. Each result reflects the current state, so a server that reconnects within the runtime leaves the report, and every new runtime connects all servers again. Invalid server configuration, such as an unsupported transport or authentication mode, still fails startup.

Claude supports both `replace` and `append` system instructions. `append`
preserves the `claude_code` preset and adds the configured content after it.

- `permission_mode`: `default`, `acceptEdits`, `bypassPermissions`, `plan`,
  `dontAsk`, or `auto`
- `reasoning_effort`: `low`, `medium`, `high`, `xhigh`, or `max`; omit to use the harness default
- `max_budget_usd`: a number greater than `0`
- `max_buffer_size`: an integer greater than or equal to `1`
- `setting_sources`: an array containing `user`, `project`, or `local`

Planning rejects unknown keys, invalid types, and invalid values before the
Claude runtime starts. When `permission_mode` is `dontAsk`, tools listed in
`tools.enabled` are pre-approved so headless runs can invoke them.
`max_buffer_size` sets the size limit the Claude Agent SDK applies to one JSON
message from Claude Code, such as a large tool result. A message over the limit
fails the invocation instead of being truncated.

## Choose an Authentication Mode

Use the mode that matches the execution environment:

| Mode | Credential Source | Recommended Use |
| --- | --- | --- |
| Claude Code login | Cached Claude.ai or Anthropic Console login | Interactive local development |
| Bearer token | `ANTHROPIC_AUTH_TOKEN` | LLM gateways or proxies that authenticate with an `Authorization: Bearer` header |
| API key | `ANTHROPIC_API_KEY` | Local development, prototypes, and controlled servers |
| Workload Identity Federation (WIF) | Anthropic profile or direct federation environment variables | CI, cloud workloads, and Kubernetes without static API keys |

Claude Code selects `ANTHROPIC_AUTH_TOKEN` before `ANTHROPIC_API_KEY`. Both
environment credentials take precedence over WIF and cached login credentials.
An empty value still occupies its precedence slot, so unset an unused variable
instead of setting it to an empty string.

Claude Code can use a Claude.ai Pro or Max login, an Anthropic Console login, or
supported enterprise providers. Refer to the
[Claude Code authentication documentation](https://docs.anthropic.com/en/docs/claude-code/getting-started)
for the current subscription and enterprise options.

## Use a Cached Claude Code Login

Authenticate Claude Code outside NeMo Fabric. The adapter inherits `HOME` and
`CLAUDE_CONFIG_DIR`, so the bundled runtime can reuse the same cached login.
NeMo Fabric does not copy the credential store into its configuration or artifacts.

## Use an API Key

Set the API key in the process that invokes NeMo Fabric:

```bash
export ANTHROPIC_API_KEY=sk-ant-api03-example
```

The adapter also forwards the selected model's `api_key_env` when the model
configuration names a different environment variable.

## Use a Compatible Custom Provider

Use `provider="anthropic"` for Claude's native authentication and endpoint
discovery. For another provider name, set both `api_key_env` and `base_url`.
The configured endpoint must implement the Anthropic Messages protocol. NeMo
Fabric maps the named credential and endpoint into Claude Code's environment;
it does not maintain a provider-name allowlist or infer provider endpoints.

## Use Workload Identity Federation

For a named WIF profile, set the profile and optional nondefault configuration
directory:

```bash
export ANTHROPIC_CONFIG_DIR=/etc/anthropic
export ANTHROPIC_PROFILE=production
```

For direct environment configuration, provide the federation rule,
organization, service account, and one identity-token source:

```bash
export ANTHROPIC_FEDERATION_RULE_ID=fdrl_example
export ANTHROPIC_ORGANIZATION_ID=00000000-0000-0000-0000-000000000000
export ANTHROPIC_SERVICE_ACCOUNT_ID=svac_example
export ANTHROPIC_WORKSPACE_ID=wrkspc_example
export ANTHROPIC_IDENTITY_TOKEN_FILE=/var/run/secrets/anthropic.com/token
```

Use `ANTHROPIC_IDENTITY_TOKEN` instead of
`ANTHROPIC_IDENTITY_TOKEN_FILE` when the platform injects the identity token as
an environment variable. Refer to the
[Anthropic WIF reference](https://platform.claude.com/docs/en/manage-claude/wif-reference)
for credential precedence, profile structure, required claims, and provider
setup.

Unset `ANTHROPIC_API_KEY` and `ANTHROPIC_AUTH_TOKEN` before using WIF. These
variables take precedence over federation even when their value is empty.

## Use Authentication with Relay

NeMo Relay does not authenticate Claude. A Relay-enabled NeMo Fabric runtime
starts one gateway as a supervised sidecar, sets `ANTHROPIC_BASE_URL` for the
Claude runtime, passes an explicit selected model endpoint to the gateway as its
Anthropic upstream, and reuses the gateway across ordered invocations.
`Fabric.run(...)` starts the same runtime, invokes it once, and stops it, so the
gateway is scoped to that single invocation. Claude still resolves its credential
through the selected mode, and NeMo Fabric does not write authentication values
to Relay configuration or artifacts.

Claude `PreToolUse` hooks set `onFailure: "block"` to block tool calls when the Relay hook fails to start, crashes, or times out. This requires Claude Code 2.1.295 or later. The pinned `claude-agent-sdk==0.2.166` bundles Claude Code 2.1.299.

NeMo Fabric supports the external NeMo Relay CLI in the `>=0.9,<0.12` range.
NeMo Fabric's `relay` extra installs only the Relay Python library and does not
install the CLI. NeMo Fabric owns sidecar supervision, Claude configuration,
and upstream selection. Relay owns the gateway transport and semantic
observability pipeline.

## Run an Agent Package

An [agent package](../../sdk/agent-packages.mdx) can declare plugins, hooks, and called agents. NeMo Fabric has no typed configuration field for them, so the loader writes each kind under a named root key of the configuration. The Claude descriptor declares the three keys, and the adapter passes what they hold to Claude.

The following example loads a video producer package that has a `remotion` plugin, a `tool-guard` hook, and a `reviewer` agent, and starts it on Claude:

```python
from nemo_fabric import Fabric, FabricConfig, load_agent_package

config = FabricConfig.from_mapping({
    "metadata": {"name": "video-producer"},
    "harness": {"adapter_id": "nvidia.fabric.claude"},
    "models": {"default": {"provider": "anthropic", "model": "your-claude-model"}},
})
report = load_agent_package("/work/video-producer", config, base_dir="/work")

runtime = await Fabric().start_runtime(report.to_config(), base_dir=report.base_dir)
```

The mapped configuration then holds the following keys. A configuration written by hand can set the same keys, with or without a package:

```json
{
  "nemo_fabric.plugins.v1": {
    "paths": ["/work/video-producer/plugins/remotion"]
  },
  "nemo_fabric.hooks.v1": {
    "entries": [
      {
        "path": "/work/video-producer/hooks/tool-guard",
        "format": "https://agent-plugins.org/schemas/1.1.0/hooks.schema.json"
      }
    ]
  },
  "nemo_fabric.agents.v1": {
    "reviewer": {
      "description": "Reviews a rendered video against the checklist and reports what fails.",
      "instructions": "Look at the contact sheet and the render you are given. Report every item that fails.",
      "max_turns": 60
    }
  }
}
```

Planning rejects a key the selected adapter does not declare and a value that does not fit the adapter's schema. When the runtime starts, the adapter checks every plugin, hook, and called agent. A part the adapter cannot use fails the start with `claude_invalid_configuration` and names the part. The adapter never leaves one out silently.

The adapter uses plugin folders and hook folders in place and does not copy them. The loader checks a package's files against its lock when it loads the package. A file that changes after the load is the file Claude Code reads or the adapter runs, so keep the package folder unchanged while the runtime lives.

### Plugins

Each path in `nemo_fabric.plugins.v1.paths` must be a folder that holds `.claude-plugin/plugin.json`, the manifest Claude Code reads. The adapter passes each folder to Claude Code as a local plugin, after the plugins it stages itself for `skills.paths` and for Relay.

When a plugin is passed, the adapter approves Claude's `Skill` tool, as it does for `skills.paths`, so that Claude can use the skills the plugin carries. A `tools.enabled` or `tools.blocked` policy still applies to the tool.

Claude Code loads everything the folder holds, not only skills. Review a plugin as code before you declare it:

- **Commands and agents.** Claude can use the commands and the agents of the plugin. The adapter does not check them.
- **Hooks in Claude's own format.** Claude Code runs the plugin's `hooks/hooks.json` itself. Those hooks can use a shell and any Claude event, and they run with the environment of Claude Code, which holds the model credential. They are not the hooks of `nemo_fabric.hooks.v1`, and what the Hooks section says about a handler does not hold for them.
- **MCP servers.** The adapter starts Claude Code with strict MCP configuration, so Claude Code uses the servers of `mcp.servers` and no MCP configuration of a plugin. Declare a server the plugin needs in `mcp.servers`.

The load report names the plugin and not what the plugin holds. For a plugin that comes from a package, the lock pins the bytes of the folder, so a change to any file of the plugin changes its digest.

### Hooks

Each entry in `nemo_fabric.hooks.v1.entries` names a hook folder and the format of its `hooks.json`. The adapter runs one format: the hooks format of the [Agent Plugins](https://agent-plugins.org/) 1.1.0 working draft. Claude Code reads hooks in a format of its own, so the adapter runs each handler itself from a Claude Agent SDK hook callback, the way the Agent Plugins format describes.

The following `hooks.json` runs one handler before each tool call:

```json
{
  "$schema": "https://agent-plugins.org/schemas/1.1.0/hooks.schema.json",
  "hooks": {
    "PreToolUse": [{"command": "./check-tool-call"}]
  }
}
```

The handler is a program in the hook folder. The following handler denies every shell command and has no opinion about any other tool call:

```python
#!/usr/bin/env python3
import json
import sys

event = json.load(sys.stdin)
if (event.get("tool_profile") or {}).get("name") == "shell":
    answer = {"decision": "deny", "reason": "This agent renders through the render-queue connector."}
    json.dump(answer, sys.stdout)
```

The adapter starts a handler as follows:

- Each event starts a new process. The adapter uses no shell.
- `command` is one token. A path that starts with `./` must be an executable file inside the hook folder. A bare name is looked up on `PATH`.
- `args` are passed as separate arguments. The adapter replaces `${PLUGIN_ROOT}` and `${PLUGIN_DATA}` in each argument and expands nothing else.
- The working directory is the hook folder.
- The environment holds `PLUGIN_ROOT`, `PLUGIN_DATA`, and operating-system variables such as `PATH` and `HOME`. No variable that holds a model credential and no value from `environment.env` reaches it. A handler runs as your user and is not confined, so it can read the files that user can read.
- `PLUGIN_ROOT` is the hook folder. `PLUGIN_DATA` is a folder for that hook under `.fabric/claude/hooks/` in the runtime's artifact root. The adapter creates the folder and does not delete it.
- The handler reads one JSON object on standard input and writes its answer to standard output. The adapter stops a handler that runs longer than 45 seconds, together with the child processes it started.

The adapter runs the following events of the format:

| Event | When It Runs | What the Handler Can Answer |
| --- | --- | --- |
| `UserPromptSubmit` | Before Claude processes a prompt. | `additional_context`, or `deny` with a reason. Claude does not process a denied prompt. |
| `PreToolUse` | Before a tool call. | `deny` with a reason, or `allow`. Claude does not make a denied call and receives the reason. An `allow` approves nothing. |
| `PostToolUse` | After a tool call returns its result or fails. | `additional_context`. |
| `Stop` | When Claude is about to finish its response. | `continue` with a reason. Claude keeps working and receives the reason. |

A handler that writes nothing has no opinion.

The event holds only the members the format defines. `tool_name` and `tool_input` are Claude's own values, unchanged. Before a tool call, the adapter also adds the format's portable view of the call, `tool_profile`, for the following Claude tools:

| Claude Tool | `tool_profile.name` | `tool_profile.input` |
| --- | --- | --- |
| `Bash` | `shell` | `command` |
| `Read` | `file.read` | `path`, from `file_path` |
| `Write` | `file.modify` | One `write` operation on `file_path` |
| `Edit`, `NotebookEdit` | `file.modify` | One `edit` operation on `file_path` or `notebook_path` |
| `WebFetch` | `web.fetch` | `url` |
| `WebSearch` | `web.search` | `queries`, with `query` as its one value |
| An MCP tool, `mcp__<server>__<tool>` | `mcp` | `name` and `arguments` |

Know these limits before you rely on a hook:

- **An `allow` does not approve a tool call.** Claude takes a hook's `allow` as approval and skips its own permission check. A package must not approve its own tool calls, so the adapter passes an `allow` to Claude as no opinion. `permission_mode` and the `tools` policy decide whether the call runs. The format lets a client's own policy stand over an `allow`.
- **A failed handler denies a tool call.** A `PreToolUse` handler that cannot start, exits with a status other than `0`, runs too long, or writes anything other than an answer the event defines denies the call. Claude receives a reason that names the hook. On the other events, a failed handler has no opinion. The adapter logs every failure.
- **`SessionStart` fails the start.** The format also defines `SessionStart`, and the adapter has no Claude hook callback for it. A `hooks.json` that lists `SessionStart`, or an event name the format does not define, fails the start.
- **A handler needs its executable mark.** A lock digest covers a file's bytes and not its mode. A handler file without its executable mark fails the start.
- **`PostToolUse` has no `tool_profile`.** The handler receives Claude's `tool_name`, `tool_input`, and tool result as `tool_result`. For a tool call that failed, `tool_result` is `{"error": "<text>"}` with Claude's error text. A tool call that was interrupted does not reach the handler.
- **An MCP tool name is Claude's spelling.** Claude writes every character of a tool name other than a letter, a digit, `_`, or `-` as `_`. For a tool with such a character, `tool_profile.input.name` differs from the name the server uses. Claude joins the server name and the tool name with `__`, and the adapter takes what follows the first `__` as the tool name. For a server whose name holds `__`, `tool_profile.input.name` starts with the rest of the server name.
- **A relative path has no `tool_profile`.** The same holds for a `WebFetch` URL that is not an absolute `http` or `https` URL.

### Called Agents

Each entry in `nemo_fabric.agents.v1` becomes one Claude subagent. The key is the agent's name. A name holds lowercase letters, digits, `_` and `-`, and does not start with `-`. That is the name rule of the package format, and the descriptor refuses any other name at planning. `description` tells Claude when to call the agent, `instructions` is the agent's prompt, and `max_turns` is its turn limit when set. The adapter passes nothing else that a called agent declares, such as a model, skills, or connectors of its own.

Claude starts a called agent with its `Agent` tool. When the configuration sets `tools.enabled`, list `Agent` there, or Claude cannot call any of them.

## Check Tool Calls and the Model with NeMo Guardrails

Set `nemo_guardrails` in the harness settings to have a NeMo Guardrails hooks server decide each tool call and the model of each invocation:

```json
{"harness": {"adapter_id": "nvidia.fabric.claude", "settings": {"nemo_guardrails": {"url": "http://127.0.0.1:8100"}}}}
```

| What | How it works |
|---|---|
| Each tool call | A PreToolUse hook posts the call to `/v1/hooks/claude-code` with `x-nemo-run-id` (the runtime id), `x-nemo-agent-name` and `x-nemo-agent-digest`. The server's answer goes to Claude Code as it is: a deny blocks the call, and `continue: false` ends the run. |
| The model | Before each invocation the adapter posts the model it is about to run, as `<provider>::<model>`, to `/v1/hooks/model-call`. A deny refuses the invocation with `claude_model_refused`, and nothing runs. |
| No answer | A server that does not answer within `timeout_seconds` (30 by default) denies the call or refuses the model. |
| The agent's name and digest | `start_agent_package` sets `agent_name` and `agent_digest` from the package. Set them yourself when you start a runtime without a package. |

The model check sees the model this adapter configures for each invocation. A model that Claude Code picks for its own background work is not asked about; check every model request in a gateway in front of the model.

## Runtime Health

`Fabric.check()` supports `live`, `active`, and `ready`. Liveness observes the owned CLI process. Active and ready require a fresh, valid `get_mcp_status()` response; reported MCP connection failures do not themselves fail readiness.

Refer to the [SDK health-check overview](../../sdk/health-checks.mdx) for shared behavior and a comparison of native evidence across adapters.

## Private HTTP model gateways with Relay

Relay-enabled runs can set `harness.settings.insecure_http_model_hosts` to an
explicit list of hostnames or IP addresses, for example
`["inference.internal", "10.0.0.10"]`. This requires NeMo Relay CLI 0.11.x.
Entries have no scheme, port, path, or wildcard; matching ignores DNS case and a
trailing dot and permits any port or path on the listed host. An explicit empty
list clears inherited HTTP trust. Omitting the setting preserves existing Relay
configuration behavior. System Relay configuration takes precedence and can
enforce an empty list.

Use this for unauthenticated inference gateways. Relay strips authorization,
API-key, cookie, and other credential headers before remote HTTP forwarding,
including credentials provided to the harness, and rejects conflicting upstream
authorization configuration. Prompts and responses travel unencrypted. HTTPS
remains the default, and MCP policy is unchanged. This option applies to
Relay-enabled Codex, Claude, and Pi runs.

## Startup Diagnostics

When the SDK fails to connect, the existing lifecycle error metadata includes `startup_diagnostics`: fixed safe summaries of recognized native permission, model, and reasoning-effort rejections. For example, Claude Code's root/sudo restriction on `--dangerously-skip-permissions` survives startup failure without changing the configured permissions or execution user.

The adapter scans at most 8,192 characters per stderr callback and retains at most one summary per recognized reason. It omits raw stderr, credential values, model IDs, prompts, and environment maps. If stderr has no recognized reason, the metadata contains an omission notice; no stderr leaves the existing error metadata unchanged. Capture ends after startup, and existing runtime journal handling remains unchanged.
