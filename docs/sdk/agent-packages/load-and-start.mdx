## Start an Agent From a Package

`Fabric.start_agent_package` loads a package and starts it in one call. It reads and checks the package, maps the agent onto your config, and returns an active `Runtime`. Nothing is started when the package is refused or when the load stops. [Agent Packages](../agent-packages.mdx#quickstart) shows a call.

`options` holds the load options by name. They are the keyword options of `load_agent_package`, and the members of the options file that `fabric-agent-ctl` reads: `entry`, `variables`, `instruction_mode`, `if_unsupported`, `if_unverified`, `check_machine`, `facts`, `expected_lock_sha256`, `bindings`, `checker` and `checker_timeout_seconds`. They are one mapping here, so they stay apart from the arguments of the start, and the same object can be that options file. A name that is not a load option is refused with `package_options_invalid` before anything is read. The other arguments, `session_ref`, `overrides` and `streaming`, mean what they mean for `Fabric.start_runtime`.

The runtime holds the load report as `runtime.agent_package_report`. A load can continue past a required thing, as [The Two Settings](#the-two-settings) describes. When it does, the call also logs one warning on the `nemo_fabric.client` logger that names each such line. To read the report before you start, use the two calls in [Load a Package in Python](#load-a-package-in-python). To decide whether the package may start, refer to [Check a Package Before It Starts](./check-before-start.mdx). In a sandbox, where no Python caller sits between the load and the start, use the command in [Load a Package in a Sandbox](#load-a-package-in-a-sandbox).

## Load a Package in Python

Pass the package folder and a complete `FabricConfig`. The config holds what the package has no field for: the harness adapter, the model endpoint and the environment.

```python
from nemo_fabric import Fabric, FabricConfig, load_agent_package

config = FabricConfig.from_mapping({
    "metadata": {"name": "release-notes-agent"},
    "harness": {"adapter_id": "nvidia.fabric.hermes"},
    "models": {"default": {"provider": "openai", "model": "served-model",
                           "base_url": "https://inference.example.com/v1",
                           "api_key_env": "MODEL_API_KEY"}},
})
report = load_agent_package("/sandbox/agent", config, base_dir="/sandbox",
                            variables={"max_turns": 8})

for check in report.digests:
    print(check.address, check.digest, check.result, check.path)

runtime = await Fabric().start_runtime(report.to_config(), base_dir=report.base_dir)
```

`report.to_config()` returns a normal `FabricConfig`. Everything after the load is the existing path: `Fabric.plan`, `Fabric.run`, `Fabric.start_runtime` and the adapters work as they do for a config written by hand.

`load_agent_package` is synchronous, like `Fabric.plan`. From asynchronous code, call it with `asyncio.to_thread`.

To check a package and read its digests without mapping it, leave the config out:

```python
report = load_agent_package("/sandbox/agent")
assert report.outcome == "verified_only"
```

The [API reference](../../reference/api/python-library-reference/nemo_fabric.agent_package.md) lists every argument.

## Load a Package in a Sandbox

`fabric-agent-ctl start` takes `--package` beside `--config`. It loads the package in the sandbox, writes the load report to a file, then sends the existing `start` request with the mapped config.

```sh
fabric-agent-ctl serve &
fabric-agent-ctl check
fabric-agent-ctl start --agent release-notes-agent \
  --config /sandbox/config.json --package /sandbox/agent \
  --package-options /sandbox/package-options.json --report /sandbox/package-report.json
```

| Flag | Meaning |
| --- | --- |
| `--package DIR` | Load this package with the config from `--config`. Requires `--config` and `--report`. Not allowed with `--request`. |
| `--report FILE` | Write the load report to this file before the start request is sent. Required with `--package`. The file is created with mode `0600` and holds the report without its `config` member. |
| `--package-options FILE` | A JSON object with the load options: `entry`, `variables`, `instruction_mode`, `if_unsupported`, `if_unverified`, `check_machine`, `facts`, `expected_lock_sha256`, `bindings`, `checker` and `checker_timeout_seconds`. Its schema is `schemas/sdk/agent-package-options.schema.json`. |
| `--package-checker JSON` | The checker program and its arguments, as one JSON array of text. It is the `checker` member of the options file, given on the command line. Name the checker in one of the two places. |

The options file is one JSON object. The following file gives a value to one variable, lets the load continue past things that are not mapped, and anchors the lock:

```json
{
  "variables": {"max_turns": 8},
  "if_unsupported": "warn",
  "expected_lock_sha256": "<the lock.sha256 of a report you keep>"
}
```

`--agent` must equal the `name` of the entry document, and so must the config's `metadata.name`.

Standard output stays one response envelope. When the loader refuses the package or the load stops, the command returns `validation_failed` and names the package code as the cause, for example `package_digest_mismatch`. It prints no path, no value and no name.

That is why the report file is required. With `if_unsupported` set to `warn`, a start goes ahead while the report lists what was warned about and left out, such as a hook or a policy. The report file is the only place those names are given, so read it after every start.

On a refusal the file is not a load report. It holds `schema_version: fabric.agent_package_refusal/v1alpha1`, `outcome: refused`, and an `error` object with the code, the subject and the message. Read `outcome` first.

The command loads and starts in one step, so nothing outside it can read the report in between. To decide before the start, name a checker. The command asks it after the package is loaded and before the start request is sent:

```sh
fabric-agent-ctl start --agent release-notes-agent \
  --config /sandbox/config.json --package /sandbox/agent \
  --report /sandbox/package-report.json \
  --package-checker '["/opt/platform/bin/check-package", "--policy", "/etc/platform/policy"]'
```

When the checker does not allow the start, the command sends nothing. It returns `validation_failed` with the cause `package_check_denied`, or `package_check_failed` for a checker that failed. The report file then has `outcome: denied` and holds the checker's answer under `checker_result`, with its reasons. Refer to [Check a Package Before It Starts](./check-before-start.mdx#ask-a-checker-program) for the contract.

Without a checker, use one of these:

- Call `load_agent_package` in the sandbox first and read the report. Then pass the report's `lock.sha256` as `expected_lock_sha256` in the options file, so the command starts only the package you looked at.
- Read the report file after the start, and stop the runtime with `fabric-agent-ctl stop` when the report lists something you cannot do without.

`Fabric.start_runtime_in` does not load packages. To start from a package in a remote environment, send the `fabric-agent-ctl start --package` command to that environment yourself.

Refer to the [runtime server command guide](https://github.com/NVIDIA/NeMo-Fabric/blob/main/sdk/python/nemo-fabric-runtime/src/nemo_fabric/runtime_server/README.md) for the full command syntax.

## What the Loader Does

The loader works in this order:

1. Read the lock and the entry document. The lock at the package root names the entry document. Use the `entry` option for an entry document that is not at the root.
2. Check each document against its schema, and check the rules no schema can state. For example, a tool must name a connector the agent has.
3. Check every part against the lock. The loader hashes each local file and folder and compares the digest with the lock. A part the documents reach must be in the lock, and the lock must hold nothing else.
4. Give each variable its value. When the entry document is a definition, read it together with its agent.
5. Check that each binding names a custom tool or a called agent the package declares.
6. Give each runtime need a status.
7. Map the agent onto the config, give each bound thing its line, and plan the result on the selected adapter.
8. Apply the two settings, `if_unsupported` and `if_unverified`, and build the report.
9. Ask the checker, when the options name one and the load is ready. Refer to [Ask a Checker Program](./check-before-start.mdx#ask-a-checker-program).

## The Two Settings

Whoever runs the agent decides what happens when a required thing does not hold. The document has no field for that.

| Setting | Applies to | Values | Default |
| --- | --- | --- | --- |
| `if_unsupported` | A required need or software package that is `not_met`, and any required declared thing that is `not_mapped`. | `stop`, `warn` | `stop` |
| `if_unverified` | A required need or thing that is `could_not_be_checked`. | `warn`, `stop` | `warn` |

With `stop`, the report has `outcome: stopped`, the `stopped_by` list names what stopped the load, and there is no config. `report.to_config()` then raises `FabricConfigError` with the code `package_requirements_unmet`. With `warn`, the load continues and the line has `effect: warned`.

The default `if_unsupported: stop` is wide. It covers every required thing that NeMo Fabric or the selected adapter does not support, not only runtime needs. A package with a policy or a token budget does not load by default on any adapter. A package with a plugin, a hook or a called agent does not load by default on an adapter that does not take it. A custom tool does not load by default until you supply it. A caller that handles such a thing itself sets `if_unsupported="warn"` and decides from the report.

The setting is for the whole load: `warn` lets every required thing through. To let through only what your platform handles, load with `warn` and check the lines of `declared` before you start. The following example treats policies and limits as handled elsewhere and stops for anything else:

```python
HANDLED_ELSEWHERE = {"policies", "limits"}

report = load_agent_package("/sandbox/agent", config, base_dir="/sandbox", if_unsupported="warn")
blocking = [
    line for line in report.declared
    if line.required
    and line.status in ("not_mapped", "not_met")
    and line.field not in HANDLED_ELSEWHERE
]
for line in blocking:
    print(line.id, line.gap, line.detail)
if blocking:
    raise SystemExit(2)
```

The two settings decide about a start. With no config nothing starts, so they are not applied: the outcome is `verified_only`, each need keeps its status, and every line has `effect: none`.
