# Release notes

Write for the person who upgrades, not for the person who made the change.

1. Read every change before you write anything.
2. Put each change under one heading: Added, Changed or Fixed.
3. Write one line for each change. Start with what the user can now do, or what no longer goes wrong.
4. Keep names of commands, options and files exactly as the change writes them.
5. Leave out a change that a user cannot see. List what you left out at the end.

## Checklist

- Every line names one change and stands on its own.
- No line promises something the change does not do.
- A change that breaks an existing use is under Changed and says what to do about it.
- The draft has no empty heading.
